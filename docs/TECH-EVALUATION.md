# 技术引进评估

> 回答两个问题：① LLM Wiki / llms.txt 这类技术要不要引进？② 还有哪些技术值得引进？
> 排序原则：**先解决真实痛点，再谈先进性**；每项都标注优先级、成本与风险。
> 优先级：P0 = 直击当前痛点且性价比最高；P1 = 明显提升质量/稳定性；P2 = 架构或体验升级。

---

## 一、关于 LLM Wiki / llms.txt 的判断

### 它是什么

`llms.txt` 是 Jeremy Howard 提出的**提议标准**：在站点根目录放一个 Markdown 文件，
用 H1 + 引用块摘要 + 若干 H2 链接清单，给 LLM 一份"策展过的地图"；
配套还有 `llms-full.txt`（全文拼接）与页面级 `.md` 双胞胎。

### 诚实的现状

- **发布侧**已广泛采用（Anthropic、Stripe、Cursor、Mintlify 等）。
- **消费侧未证实**：Google 公开表示不使用它，多项研究显示多数 llms.txt 几乎没有爬虫流量。
- 结论：**它是"给愿意抓取的智能体一个干净入口"，不是"控制爬虫"也不是"AI 搜索排名手段"。**

### 对本项目的结论：可引进，但不要作为主线

**不适合**指望它做的事：让外部 AI"了解 EduForge"、带来可见度——我们是本地部署的教学工具，不是文档站。

**值得做的两点**（低成本，收益确定）：

| 用法 | 做法 | 价值 |
|---|---|---|
| **消费侧**：把依赖的官方文档做成机读件 | 在 `docs/references/` 放 `uv-llms.txt`、`vue-llms.txt`、`element-plus-llms.txt` 等 | 这正是 OpenAI 那篇 Harness 文章里的做法：让 AI 不必联网猜 API |
| **发布侧**：生成一份仓库级索引 | 提供 `llms.txt`（严格按规范：H1 + 引用块 + H2 链接清单），指向 AGENTS.md 与各 docs | 给外部 AI 工具一个结构化入口；同时倒逼我们保持文档结构清晰 |

> ⚠️ 不要为了 llms.txt 再造一套文档体系。**AGENTS.md + docs/ 地图已经承担了"给 AI 看"的职责**，
> llms.txt 只是它的一个对外投影，应由脚本生成而非手工维护，否则必然腐烂。

**优先级：P2（低成本，顺手做）**。

## 二、P0：直击当前痛点

### 1. 统一扩展点：MCP + Tool/Skill 注册中心

- **痛点**：前端里 MCP、Skill 不知道怎么加、怎么扩展能力 —— 这是"扩展能力没有统一入口"的结构性问题。
- **做法**：不要在每个页面各写一套接入。建**单一扩展层**——
  - `Tool`：原子能力（生成、检索、导出、联网查询…），统一签名与权限声明；
  - `Skill`：把若干 Tool + 提示词模板编排成可复用的"教学技能"（如"出当堂检测题"）；
  - MCP 客户端作为 Tool 的一种**来源**：接上 MCP server 即可把外部工具引入同一注册表；
  - 前端只做：列出已注册能力 → 启用/禁用 → 展示参数表单。UI 由注册表驱动，不再硬编码。
- **成本**：中。**风险**：低（先做内部 Tool 注册，MCP 作为适配器后接，可渐进）。
- **收益**：扩展能力从此只需"注册"，不改前端；也天然支持后续接校内系统。

### 2. CI：GitHub Actions 跑既有验证

- **痛点**：176 项测试靠人自觉跑；仓库已在 GitHub，却没有任何自动化。
- **做法**：一个 workflow——后端三条 smoke + `npx vite build --outDir .verify-dist` 编译校验
  （**注意：绝不能跑会清空 dist 的命令**，见 [CONSTRAINTS.md §A1](CONSTRAINTS.md#a1-禁止直接-npm-run-build)）。
- **成本**：低。**风险**：无。**收益**：把"改坏了"挡在合并之前，是 Harness 支柱二的机械化落点。

### 3. 结构化输出（JSON Schema 约束 + Pydantic 边界校验）

- **痛点**：本项目真实踩过的大坑——模型输出被截断/不合法 → 解析失败 → "生成成功但内容全空"。
- **做法**：所有生成接口定义 Pydantic 模型 + JSON Schema；优先用平台的 structured output / response_format；
  解析失败走**显式重试**（带更短的字段要求），而不是静默兜底。
- **成本**：中。**风险**：低。**收益**：从根上消除一类最难查的故障。

### 4. 前端最小测试：Vitest + Playwright 冒烟

- **痛点**：前端目前**零测试**（`package.json` 只有 dev/build/preview），是稳定性最大缺口。
- **做法**：先只覆盖关键路径——生成请求发出 → 进度/结果渲染 → 预览与下载可用；再加合规报告组件的单测。
- **成本**：中。**风险**：低。**收益**：改前端不再靠肉眼看。

## 三、P1：明显提升质量与稳定性

| 技术 | 解决什么 | 成本 | 备注 |
|---|---|---|---|
| **Ruff + pyright/mypy** | 目前两者**都没有**，静态约束全靠自觉 | 低 | 配合 Harness 支柱二；建议 linter 报错里直接附修复指引 |
| **集中配置校验**（pydantic-settings） | 启动时校验环境变量、缺失即快速失败 | 低 | 避免"配错了跑到一半才炸" |
| **结构化日志 + 请求 ID** | 排查"生成失败/很慢"没有抓手 | 低 | 先落盘 JSON 日志；本地可观测栈（Vector+Victoria）成本偏高，后置 |
| **生成质量 Evals** | 现在只有 RAG 评测；改 prompt 后"变好还是变坏"无法度量 | 中 | 建教案/PPT 的 golden set + 人工评分维度 |
| **产物契约/快照测试** | 四路生成的 JSON 结构改动易互相踩坏 | 低 | schema 快照 + 关键字段断言 |
| **结果缓存 + 任务幂等** | 重复生成浪费额度；重试会产生重复产物 | 中 | 缓存设 TTL；任务带幂等键 |
| **SSE 流式输出** | "生成很久没反应"是体验差的直接来源 | 中 | 先做进度事件流，不必一开始就流式正文 |

## 四、P2：架构与体验升级

| 方向 | 说明 |
|---|---|
| **收敛 4 条 LLM 调用路径为 1** | 历史包袱，是插桩漏接、行为不一致的根源。收敛后出校合规只需守一个口子 |
| **编排显式化** | 用 LangGraph 或自研，把"规划→生成→Critic 审查→重生成"固化；你在视频检查项目已用 LangGraph，经验可复用 |
| **向量库简化** | ChromaDB 换 sqlite-vec / pgvector 可降低部署复杂度；或保持但容器化并固定版本 |
| **离线部署包** | 学校内网最关心：Docker Compose 一键 + 预置本地模型权重，甚至单文件分发 |
| **Skill/Tool 市场化的 UI** | 承接 P0-1：能力卡片、启用开关、参数表单由注册表自动生成 |
| **llms.txt 生成脚本** | 承接第一节：由 docs 结构自动生成，不做手工维护 |

## 五、明确不建议引进的

| 不建议 | 理由 |
|---|---|
| 重型 Agent 全家桶（大而全的编排框架） | 违背"依赖极简、可内化进仓库推理"；把不可预测性引进来，与 Harness 目标相反 |
| 微服务拆分 | 本地优先单机场景，单体更简单、更好部署 |
| 用模型识别敏感信息 | 悖论：识别本身就要把原文送进模型（见 [CONSTRAINTS.md §B3](CONSTRAINTS.md#b3-敏感识别必须保持本地规则不得改用模型识别)） |
| 用 LLM 做教学合规的最终判定 | 保持规则为判定主体；LLM 只能做"修改建议"，且必须可关闭 |
| 盲目跟进新标准（含 llms.txt 的过度投入） | 先问：它解决我们哪个真实痛点？没有答案就放到 P2 |

## 六、建议的推进顺序

```
第 1 步  CI（Actions 跑 176 项 smoke + 前端编译校验）        ← 半天，立刻见效
第 2 步  Ruff/pyright + 集中配置校验                        ← 让约束从"文档"变成"机器"
第 3 步  结构化输出 + Pydantic 边界校验                     ← 消除空内容类故障
第 4 步  Tool/Skill 注册中心（前端由注册表驱动）             ← 解决 MCP/Skill 扩展痛点
第 5 步  前端 Vitest + Playwright 冒烟                      ← 补最大测试缺口
第 6 步  SSE 进度流 + 结果缓存                              ← 体验与成本
第 7 步  收敛 LLM 调用路径 → 编排显式化 → 离线部署包
```

每一步都应：**先写清约束与验收，再动手**（Harness 的顺序永远是"先建缰绳，再放马"）。
