# Harness Engineering 在本项目的落地

> 目标：让**任何** AI 编码工具（Claude Code / Cursor / Codex / Copilot / WorkBuddy 等）
> 在这个仓库里工作时，都收敛到同一套行为方式，而不是各写各的、把项目改得面目全非。

## 一、概念

Harness（马具）本义是驾驭马匹的整套结构。Harness Engineering 的核心主张是
**"人类掌舵，智能体执行"**：不去优化模型本身，而是围绕模型搭建一整套
**约束机制 + 反馈回路 + 知识环境**，让原本不可预测的智能体在高可靠环境下稳定产出。

它是这条演进路线的第三步：

```
提示词工程（教模型听懂话）
  → 上下文工程（让模型看到全貌）
    → Harness Engineering（给智能体一套能自己干活的工程环境：有工具、有规则、有反馈）
```

三大支柱：

| 支柱 | 要解决的问题 | 典型手段 |
|---|---|---|
| **上下文工程** | AI 在正确的时间拿到正确的信息 | 仓库即记录系统、文档做"地图"而非"百科全书"、渐进式披露 |
| **架构约束** | 防止生成代码走形 | 分层与依赖方向、机械强制的 linter、**品味不变式** |
| **熵管理** | 防止长期漂移与技术债堆积 | 黄金原则入仓、定期 GC 式清理、doc-gardening |

关键认知：**模型是通用商品，真正的竞争力是你围绕模型搭的这套工程体系。**
同一个模型，在不同 Harness 下产出质量天差地别。

## 二、为什么要为本项目建 Harness

- 项目会长期由**不同的 AI 编码工具**接力开发，每个工具默认都有自己的偏好与"想法"。
- 项目有若干**一旦破坏代价极高**的隐藏约束（dist 是生产目录、闸门不能阻断、
  出校插桩不能漏接），这些知识**只存在于对话里就等于不存在**。
- 本项目已具备良好的反馈基础（176 项离线测试 + 100 条评测集），
  只差把"规则"和"验证"串成一个闭环。

## 三、本仓库 Harness 的现状与缺口

### 支柱一：上下文工程

| 已有 | 缺口 | 下一步 |
|---|---|---|
| `AGENTS.md` 作为唯一入口（~100 行，只做地图） | 深层文档尚未按"渐进式披露"分层 | 保持 AGENTS.md 简短，细节只放 `docs/` |
| `docs/` 有 ARCHITECTURE / RAG / CONSTRAINTS / DEVELOPMENT / TECH-EVALUATION | 缺决策记录（ADR）与执行计划目录 | 建 `docs/decisions/`、`docs/exec-plans/` |
| 核心约束写进了仓库 | 部分历史决策仍在对话里 | 遇到即补，见下方"知识入仓"纪律 |

**纪律：知识必须入仓。** 任何非显而易见的共识（为什么这么做、踩过什么坑），
若不落成仓库里的 Markdown，下一次换工具/换会话就全部丢失。

### 支柱二：架构约束

| 已有 | 缺口 | 下一步 |
|---|---|---|
| 硬约束清单 [`CONSTRAINTS.md`](CONSTRAINTS.md)（含**原因**，便于自行判断） | 目前靠"读文档自觉遵守" | 逐步机械化为 linter / CI 检查 |
| LLM Harness 统一入口（重试/超时/熔断/追踪/降级） | 4 条调用路径的历史包袱 | 收敛为单一调用入口 |
| 静态回归校验：安全插桩完整性、max_tokens 下限 | 仅覆盖两条规则 | 把更多"品味不变式"写成测试 |

**推荐做法（来自 OpenAI 实践）**：linter 的报错信息里**直接写修复指令**，
让 AI 拿到报错就知道该怎么改，而不是再去翻文档。

### 支柱三：熵管理

| 已有 | 缺口 | 下一步 |
|---|---|---|
| 176 项离线测试作为回归基线 | 无自动 GC | 定期跑"清理任务"：扫死代码、过时注释、命名漂移 |
| 已清理 8 份过程性文档 | 无防回流机制 | 把"文档边界"写进 [`CONSTRAINTS.md §F1`](CONSTRAINTS.md#f1-文档边界什么该入库什么不该) |
| 误报反例进测试 | — | 新增规则必须同步补反例，否则拒绝合并 |

## 四、AI 在本仓库的标准工作循环

```
1. 读 AGENTS.md（红线 + 地图）
2. 按地图只读需要的文档（不要全量塞进上下文）
3. 改代码
4. 跑三条 smoke（176 项）+ 相关专项验证
5. 把"为什么这么改"写进提交信息；非显而易见的取舍写进 docs/
6. 若发现文档与代码不符 —— 改文档，而不是将就代码
```

**合并理念**：保持小而快的改动粒度；测试偶发失败优先重跑而非阻塞。
纠错成本低，等待成本高。

## 五、可度量的基线（改动后不得低于此线）

| 指标 | 当前值 | 来源 |
|---|---|---|
| 离线冒烟测试 | 176 项全绿（70 + 77 + 29） | `scripts/smoke_*.py` |
| RAG Recall@1 | 0.967 | `make eval` |
| RAG MRR@5 | 0.972 | `make eval` |
| RAG 漏拒率 | 0.000 | `make eval` |
| 前端可访问性 | 后端 `/` 返回 200 | 人工/脚本 |

## 六、维护这份 Harness 的责任

- 任何人（或 AI）发现**文档与代码不符**，直接改文档。
- 任何新踩的坑，补进 [`CONSTRAINTS.md`](CONSTRAINTS.md) 或 [`DEVELOPMENT.md`](DEVELOPMENT.md) 的故障排查。
- `AGENTS.md` 只增长"地图"，不增长"细节"——细节溢出就搬到 `docs/`。
